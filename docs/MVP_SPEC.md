# Kazakh Model Watch — техническая спецификация MVP

Дата: 2026-10-20. Версия протокола: `mvp-v2-non-thinking`, утверждена владельцем.

Изменения относительно `mvp-v1`: обязательный запрос `reasoning.enabled=false` для обеих моделей и определение 128 как запрошенного API-лимита генерации. Датасет, scoring, нормализация, инструкция и политика повторов сохранены. Название версии обозначает запрос отключения reasoning; фактическое внутреннее поведение upstream не гарантируется.

Цель: сравнить минимум две реальные API-модели на небольшом, вручную проверенном наборе заданий на казахском языке. Результат — проверяемые ответы, метрики и Markdown leaderboard. Это оценка конкретного набора заданий; она не измеряет владение казахским языком в целом.

Документ определяет будущую реализацию. Примеры ниже описывают формат данных и правила оценки, а не результаты моделей.

### Стратегия репозитория и порядок работ

GitHub-репозиторий остаётся **PRIVATE** до выполнения acceptance criteria MVP и release review. Этот файл — основная техническая спецификация; приоритет первой реализации — минимальный работающий pipeline и реальные результаты минимум двух моделей. Репозиторий развивается в существующей структуре, без дополнительных сервисов, framework плагинов и лишних уровней абстракции.

Текущий этап — только настройка репозитория и документации; реализация benchmark выполняется отдельно. API-ключи, `.env` и конфиденциальные данные не включаются в Git даже при PRIVATE visibility. `results/` игнорируется по умолчанию; конкретный завершённый запуск включается в репозиторий адресно после проверки его содержимого. Приватность репозитория не заменяет проверку данных и секретов.

До изменения visibility на PUBLIC проводится release review: выполнение acceptance criteria, проверка файлов и истории Git на секреты и данные работодателя, проверка происхождения/прав использования датасета, scoring и артефактов реального запуска. Итог review и решение владельца фиксируются; только после этого разрешена публичная публикация. Завершение MVP не запускает публикацию автоматически.

## 1. In Scope / Out of Scope

### In Scope

- **24 задания: по 8 в `numbers`, `dates`, `morphology`.** Это укладывается в диапазон 20–30 и даёт категориям одинаковый вес.
- `numbers`: короткие вычисления и понимание чисел; ответ — одно целое число. `dates`: понимание явно заданных календарных дат; ответ — `YYYY-MM-DD`. `morphology`: образование одной словоформы по явному указанию; ответ — одно слово. Ограниченный формат позволяет оценивать ответы без субъективного судьи.
- Казахские задания в кириллице, проверенные человеком, владеющим казахским языком. Условия, эталоны и допустимые варианты фиксируются до первого оценочного запуска.
- Минимум две различные реальные текстовые модели через официальные API. Конкретные `provider` и `model_id` выбираются и проверяются при реализации, затем сохраняются в конфигурации и результатах. Два имени одного и того же backend не считаются двумя моделями.
- Accuracy, строгий exact match, latency, coverage и число ошибок; стоимость — только при проверяемых исходных данных.
- Локальный CLI, результаты в JSON и CSV, Markdown leaderboard, `pytest` и GitHub Actions. Файлов достаточно для такого объёма данных.

### Out of Scope

- Обучение, fine-tuning, RAG, агенты, инструменты, поиск, multimodal и самостоятельный хостинг моделей.
- Web UI, сервер, база данных, очередь задач, распределённые запуски и автоматический выбор лучшей модели.
- LLM-as-a-judge, fuzzy matching, embeddings, частичный балл и автоматическое расширение списка правильных ответов.
- Массовый сбор данных, закрытые корпуса и любые данные работодателя: документы, переписка, клиентские сведения и внутренние примеры.
- Подбор prompt под отдельную модель, best-of-N, большие статистические исследования и утверждения о превосходстве на языке в целом.
- `simple reading comprehension` в текущем протоколе: выбрана `morphology`. Замена третьей категории возможна только в новой версии датасета и протокола, с отдельным leaderboard, чтобы состав сравнения оставался понятным.

## 2. Минимальный pipeline

Один процесс: **валидация → загрузка конфигурации → API-вызовы → сохранение → scoring → агрегация → leaderboard**. Внутри одного небольшого Python-пакета нужны только загрузчик, runner, адаптеры API, scorer и экспорт; отдельные сервисы и framework плагинов не требуются.

1. Прочитать `data/benchmark.jsonl`; проверить схему, уникальность ID, 24 задания, баланс категорий и отметки ручной проверки. Ошибка в данных останавливает запуск до платных вызовов.
2. Прочитать `config/models.json`: модели, имена переменных окружения с ключами, общие параметры и версии протокола/датасета. Проверить совместимость параметров с API; неподдерживаемые настройки не заменять молча. Наличие самих ключей проверяется только в `run`, чтобы offline-валидация работала без секретов.
3. Создать отдельный `run_id` и каталог `results/<run_id>/`; сохранить manifest и копии датасета и публичной конфигурации. Каталог предыдущего запуска не перезаписывать.
4. Перемешать задания с фиксированным `order_seed=42`. Последовательно вызвать все модели для каждого задания; порядок моделей циклически менять между заданиями. Это ограничивает нагрузку и уменьшает преимущество модели, всегда вызываемой первой.
5. После каждой пары модель/задание сохранить запись с исходным ответом и всеми попытками; JSON обновлять атомарной заменой файла. При прерывании оставить `run_status=incomplete`; отсутствующие записи учитывать как `not_run`. Возобновление и объединение запусков не нужны в MVP: повторный оценочный запуск получает новый `run_id`.
6. Посчитать метрики по сохранённым ответам, экспортировать JSON/CSV и сгенерировать leaderboard. После обработки всех пар установить `run_status=complete`, даже если отдельные вызовы завершились ошибкой. Повторный scoring и генерация отчёта работают без сети и ключей.

Будущий CLI должен поддерживать три операции: `validate` для данных и конфигурации, `run` для реального сравнения и `report` для пересчёта сохранённого запуска. Это разделяет платную генерацию и дешёвую проверку результатов без усложнения архитектуры.

| Артефакт запуска | Содержание |
| --- | --- |
| `manifest.json` | Идентичность запуска, версии, хеши, окружение и параметры |
| `dataset.jsonl`, `config.json` | Точные публичные входные данные запуска, без секретов |
| `responses.json` | Одна запись на пару модель/задание, включая ошибки и историю попыток |
| `responses.csv` | Те же итоговые поля; вложенные `attempts`, `usage` и `error` — JSON-строки |
| `metrics.json`, `metrics.csv` | Общие метрики и строки по каждой категории |
| `leaderboard.md` | Таблица этого запуска с ссылками на исходные артефакты |

JSON — UTF-8, CSV — UTF-8 с корректным экранированием кавычек, запятых и переводов строк. `null` в JSON и пустая ячейка CSV означают отсутствие значения; ноль является измеренным значением. Общий `LEADERBOARD.md` в корне формируется только из завершённого выбранного запуска и ссылается на его каталог. Автоматический отчёт не должен выдумывать значения для пропущенных полей.

## 3. Формат JSONL-датасета и обязательные поля

`data/benchmark.jsonl`: UTF-8 без BOM, один JSON-объект на непустую строку, без внешнего массива и комментариев. Пустой существующий `data/benchmark.json` не является датасетом; новый JSONL будет создан на этапе реализации. JSONL облегчает проверку отдельных заданий и просмотр diff.

| Поле | Тип и обязательное правило |
| --- | --- |
| `id` | Непустая уникальная строка, например `numbers_001`; сохраняется при исправлении того же задания |
| `category` | Только `numbers`, `dates` или `morphology` |
| `language` | Строка `kk` |
| `prompt` | Полное условие на казахском, включая требуемый формат ответа; контекст при необходимости находится здесь |
| `reference_answer` | Непустая строка с одним каноническим эталоном |
| `accepted_answers` | Непустой массив строк, включающий `reference_answer`; содержит только заранее проверенные эквиваленты |
| `answer_type` | `integer` для numbers, `iso_date` для dates, `word` для morphology |
| `source` | Объект с `type` (`author_created` или `public`) и `attribution`; для `public` обязательны также `url` и `license` с подтверждённым правом использования |
| `review` | Объект: `status="verified"`, непустой `reviewer_id` (псевдоним), `reviewed_at` (`YYYY-MM-DD`), `note` с кратким обоснованием эталона и вариантов |

Пример одной строки; это иллюстрация схемы, не свидетельство уже выполненной ручной проверки:

```jsonl
{"id":"numbers_001","category":"numbers","language":"kk","prompt":"Екіге үшті қосқанда қанша болады? Жауапты тек бүтін санмен жазыңыз.","reference_answer":"5","accepted_answers":["5"],"answer_type":"integer","source":{"type":"author_created","attribution":"Оригинальное задание для публичного benchmark."},"review":{"status":"verified","reviewer_id":"reviewer_example","reviewed_at":"2026-10-14","note":"Иллюстрация: 2 + 3 = 5; при включении в датасет требуется реальная проверка."}}
```

Валидация проверяет типы всех полей, допустимые enum, согласованность категории и `answer_type`, корректность календарных дат, отсутствие пустых эталонов и дубликатов вариантов после нормализации. Эталоны numbers — `0` либо целое с необязательным минусом, без ведущих нулей; dates — существующая дата в `YYYY-MM-DD`; morphology — одна словоформа в казахской кириллице, при необходимости с дефисом.

Проверяющий самостоятельно решает каждое задание, сверяет эталон и варианты, проверяет казахскую формулировку, отсутствие неоднозначности и происхождение текста. Для дат явно указаны год и исходная дата; относительные условия вроде «бүгін» без опорной даты исключены. Неоднозначные словоформы уточняются в условии или исключаются. Датасет состоит из оригинальных либо разрешённых публичных примеров и проходит отдельную проверку на отсутствие данных работодателя.

Версия датасета (`kk-mvp-v1`) хранится в конфигурации и manifest. Изменение условия, эталона, вариантов или состава повышает версию и SHA-256; прежние результаты сохраняются отдельно. Это предотвращает сравнение оценок на незаметно изменённых заданиях.

## 4. Интерфейс вызова моделей

Контракт адаптера: **`generate(request) → response`**. Это описание интерфейса, без Python-реализации. Один адаптер обслуживает особенности одного провайдера; runner отвечает за таймер, повторы и запись результатов.

| Вход `request` | Требование |
| --- | --- |
| `provider`, `model_id` | Точный провайдер и запрашиваемый ID; предпочитать доступную фиксированную версию модели |
| `prompt` | Одна общая инструкция + пустая строка + `prompt` задания; история диалога отсутствует |
| `temperature` | `0` для всех моделей |
| `max_output_tokens` | `128` для всех моделей; отправляется как API-параметр `max_tokens=128` |
| `timeout_s` | `60` на попытку |
| `reasoning` | Только `{"enabled": false}`, обязательно для обеих моделей |

Общая инструкция, неизменная для всех заданий и моделей:

> Тапсырманы орындаңыз. Жауапты сұралған форматта ғана жазыңыз. Түсіндірме қоспаңыз.

Передаётся один user message; system message, few-shot, tools, streaming и provider seed не используются. Для обеих моделей передаётся одинаковый запрос `reasoning.enabled=false`; дополнительные effort, exclude и reasoning.max_tokens запрещены. Выбираются модели, поддерживающие профиль; передаются `provider.require_parameters=true` и `provider.allow_fallbacks=false`, без автоматической замены параметров или модели. `top_p` и другие параметры не задаются; применённые API defaults документируются. Разные токенизаторы и backend не означают одинаковый вычислительный бюджет — сравнивается общий режим короткого ответа. Любое обязательное дополнительное поле API фиксируется в конфигурации с пояснением; изменение общего профиля требует новой версии протокола.

`max_tokens=128` фиксирует запрошенный API-лимит генерации. На большинстве провайдеров он охватывает reasoning и видимый ответ вместе; фактический учёт зависит от backend. Протокол не гарантирует отдельный лимит в 128 токенов именно видимого ответа, одинаковый внутренний вычислительный бюджет или финансовый hard cap. Источники: [OpenRouter API Parameters](https://openrouter.ai/docs/api_reference/parameters), [Reasoning Tokens](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

Поддержка параметров в metadata и `require_parameters=true` ограничивают маршрутизацию, но не доказывают внутреннее поведение upstream. Нулевой reasoning counter или отсутствие reasoning в ответе не доказывают его отключения. Если фактический upstream не сообщён и не сохранён, он остаётся неизвестным; одинаковый payload не закрепляет одного upstream на все вызовы. См. [Provider Selection](https://openrouter.ai/docs/guides/routing/provider-selection).

Для нового реального сравнения используются `qwen/qwen3.5-9b` и `google/gemini-3.1-flash-lite` через OpenRouter. Утверждение протокола не переводит модели в `ready`/`profile_verified=true` и не разрешает live. До benchmark нужны отдельный review live-свидетельств, human verification датасета и разрешение расходов.

Старый `mvp-v1` без reasoning остаётся допустимым. Промежуточные snapshots `mvp-v1` с reasoning из PR #10 сохраняют offline-пересчёт с прежней версией; новый live benchmark с таким сочетанием отклоняется до ключей, адаптеров и HTTP. Legacy mock-demo остаётся синтетическим. Старые файлы не переименовываются в v2, результаты разных версий не объединяются.

| Выход `response` | Требование |
| --- | --- |
| `status` | `ok`, `api_error`, `timeout`, `empty_response`, `truncated` или `not_run` |
| `raw_response` | Видимый текст без очистки, либо `null`, если текста нет; хранить текст и при обрыве |
| `requested_model_id`, `returned_model_id` | Запрошенный и возвращённый API ID; последний — `null`, если API его не сообщает |
| `request_id`, `finish_reason` | Значения API либо `null` |
| `usage` | Только сообщённые API счётчики токенов по типам, иначе `null`; не оценивать по длине текста |
| `latency_ms` | Длительность выбранной успешной попытки; `null`, если её нет |
| `total_elapsed_ms` | Полное время пары модель/задание с повторами и ожиданиями |
| `attempts`, `error` | История вызовов с длительностью, статусом, usage и очищенными от секретов ошибками; финальная ошибка либо `null` |

`ok` означает полный ответ с видимым текстом, содержащим хотя бы один непробельный символ. Отказ модели с текстом остаётся `ok` и оценивается как неверный ответ. `empty_response` означает отсутствие такого текста, `truncated` — обрыв по лимиту, `not_run` — отсутствие вызова. У `not_run` нет попыток, а измеренное время равно `null`, а не нулю.

При запрошенном отключении положительные reasoning counters или непустой reasoning-текст дают `api_error/reasoning_not_disabled` с сохранением видимого ответа и usage; `length` сохраняет `truncated`, `content_filter` — `api_error/content_filtered`. Сообщённые counters не исправляются догадками. `completion_tokens >128` — наблюдаемая аномалия, сама по себе не доказывающая превышение видимого лимита; она не заменяет `stop` на `length`. В benchmark неизвестный usage остаётся неизвестным и сам по себе не меняет status полного ответа. Это ограничивает выводы о фактическом reasoning.

Не более двух попыток: исходный вызов и один повтор только при timeout, сетевом сбое, HTTP 429 или 5xx. SDK-повторы отключаются, чтобы не создавать скрытые попытки. При повторе ожидание — 2 секунды либо больший `Retry-After` до 60 секунд; при большем значении повтор отменяется и сохраняется ошибка. 4xx, кроме 429, пустой или неверный ответ и обрыв по лимиту не повторяются. Выбирается первый полученный полный непустой ответ; качество ответа не влияет на решение о повторе. Такой порядок не превращает retry в дополнительную попытку решить задание.

На 24 задания × 2 модели планируются 48 исходных вызовов, максимум 96 POST с разрешёнными повторами. Это отдельное финансовое разрешение. Limited smoke — диагностика одного фиксированного задания, максимум два POST без повторов; его бюджет не переносится на benchmark. Неизвестные counters, reasoning и остальные условия остановки smoke описаны в [LIMITED_SMOKE_PROPOSAL.md](LIMITED_SMOKE_PROPOSAL.md).

Ключи берутся только из переменных окружения или GitHub Secrets; в конфигурации сохраняются лишь имена переменных. Прямые API-вызовы обязательны для финальной проверки; mock-адаптер нужен только для тестов. Эталон, варианты и `review` никогда не входят в запрос модели.

## 5. Правила scoring и нормализации ответов

Scoring детерминированный, бинарный и оценивает весь ответ. `reference_answer` задаёт строгий формат, а `accepted_answers` — заранее согласованные эквиваленты.

### Exact match и accuracy

- **`exact_match = 1`**, если `status=ok` и `raw_response` в точности равен `reference_answer` как последовательность Unicode-символов. Пробелы, регистр и переводы строк не удаляются. Это отдельно измеряет соблюдение формата.
- **`correct = 1`**, если `status=ok` и нормализованный полный ответ совпадает хотя бы с одним нормализованным элементом `accepted_answers`. **Accuracy** — доля таких заданий; это нормализованная оценка правильности, а не произвольная семантическая проверка.
- В остальных случаях оба значения равны `0`. Отказ, пустой ответ, обрыв, API-ошибка и `not_run` не исключаются из знаменателя. Не выбирать правильное число из объяснения и не засчитывать один из нескольких противоречащих ответов.

### Нормализация `kk-short-v1`

Порядок одинаков для ответа и эталонов:

1. Unicode NFC: объединить канонически эквивалентные последовательности символов. Выбор NFC сохраняет различия совместимости, которые может убрать NFKC; см. [Unicode UAX #15](https://www.unicode.org/reports/tr15/).
2. Удалить Unicode whitespace только по краям; внутренние последовательности whitespace заменить одним обычным пробелом. Zero-width символы не считать whitespace и не удалять.
3. Применить Unicode `casefold` для сравнения без учёта регистра. Версию Python и его Unicode database записать в manifest.

Других преобразований нет. Не удалять пунктуацию, кавычки, Markdown, дефисы, суффиксы или объяснения; не выполнять транслитерацию и не заменять `ә/а`, `ғ/г`, `қ/к`, `ң/н`, `ө/о`, `ұ/ү/у`, `і/и` или похожие латинские буквы. Иначе нормализация могла бы скрыть языковую ошибку.

Для numbers не применять float, округление или допуск: `5` и `5.0` различаются. Для dates не угадывать порядок дня и месяца: `2026-03-05` и `05/03/2026` различаются. Для morphology альтернативы допустимы только при ручной проверке и включении в `accepted_answers` до запуска. После просмотра ответов менять правила в текущем leaderboard запрещено; исправление эталона оформляется новой версией и пересчётом всех моделей по одной версии.

Контрольные примеры правил, без результатов моделей: для эталона `5` ответ `" 5\n"` даёт accuracy-балл 1 и exact match 0; `"Жауап: 5"` и `"5 немесе 6"` дают 0 по обеим метрикам. Для эталона `қалаға` ответ `калага` неверен. Для даты неверное форматирование не исправляется автоматически.

### Агрегация, latency и стоимость

- На модели с `N=24`: `accuracy = sum(correct) / N`; `exact_match_rate = sum(exact_match) / N`; `coverage = count(status=ok) / N`. Публиковать и дроби, и проценты. По каждой категории использовать её полный размер, равный 8. Общая accuracy — micro average; при равных категориях она совпадает с macro average.
- Раздельно публиковать количества статусов. Метрики незавершённого запуска допустимы только с явной отметкой `incomplete`; его нельзя публиковать как финальный leaderboard.
- Latency измерять монотонным таймером от начала API-вызова до полного получения ответа, без scoring и записи файлов. Среднее и медиану считать по `status=ok`, включая неверные ответы, с явным `latency_sample_count`; при отсутствии успешных ответов значения `null`. Время неуспешных попыток хранить в `attempts`, а общую длительность с retries — в `total_elapsed_ms`. Это отличает скорость ответа от последствий сбоев.
- Стоимость пары модель/задание — либо сумма подтверждённых начислений API, либо расчёт по официальным usage и тарифу, действовавшему на дату вызова для точной модели и режима. Сохранять `cost_method`, валюту, `pricing_source_url`, дату тарифа, дату получения источника, единицы и ставки либо ссылку/ID начисления. Учитывать отдельно все оплачиваемые типы токенов, cached input и все попытки; не подставлять обычный тариф вместо неизвестного.
- Если usage, тариф, тарификация повтора или оплачиваемый reasoning неизвестны, `cost=null` с `cost_unknown_reason`. Отсутствие usage при timeout не доказывает бесплатность вызова. Общая стоимость модели доступна только при подтверждении стоимости всех попыток; иначе `null`, без выдачи неполной суммы за итог. В leaderboard неизвестная стоимость отображается как `N/A`, не как `0`.

Leaderboard содержит provider/model ID, правильные ответы `k/N`, accuracy, exact match, coverage, ошибки, среднюю/медианную latency в ms с размером выборки и подтверждённую стоимость либо `N/A`. Порядок строк — по accuracy по убыванию; при равенстве показывается одинаковое место, строки упорядочиваются по provider/model ID. Latency и цена не используются для заявления о превосходстве. Под таблицей — разбивка по категориям, параметры, версии, дата запуска и ссылка на артефакты. До реального запуска таблица не содержит вымышленных показателей.

## 6. Честность и воспроизводимость сравнения

- **Один замороженный набор и профиль.** Все модели получают идентичный видимый текст, одинаковые ограничения и один ответ на задание. Никаких эталонов в prompt, истории между заданиями и индивидуального prompt tuning. Публичный benchmark может попасть в обучающие данные; исключить это нельзя, поэтому ограничение явно указывается в отчёте.
- **Один полный запуск сравнения.** Использовать одну машину, общий временной интервал, фиксированный порядок и чередование моделей. Указать runner/ОС, время начала и завершения в UTC; latency включает сеть и не является измерением скорости чистого inference. Встроенное кэширование провайдера и известные defaults отмечаются; локально повторно использовать ответы для нового запуска нельзя.
- **Все исходные свидетельства сохранены.** Каждая запись содержит `run_id`, `item_id`, категорию, provider/model ID, точный prompt, raw и normalized response, статус, баллы, usage, время, retries и стоимость/причину отсутствия. Убедиться, что число записей равно `N × число моделей`, включая сбои.
- **Manifest позволяет повторить протокол.** Обязательны `run_id`, `run_status`, UTC timestamps, dataset/protocol/scoring/normalization versions, SHA-256 датасета, конфигурации и общей инструкции, Git commit и `working_tree_dirty`, версии Python/Unicode/зависимостей, ОС/runner, `order_seed`, фактический порядок заданий и моделей, запрошенные/возвращённые ID и применённые настройки. Для опубликованного запуска рабочее дерево чистое, зависимости зафиксированы; mutable model alias помечается как ограничение воспроизводимости.
- **Повторяемость имеет два уровня.** Offline scoring одного артефакта обязан давать те же баллы и числовые метрики. Повторный API-запуск при temperature 0 может дать другой текст и latency; точная идентичность не гарантируется, даже если модель имеет фиксированное имя. Старые и новые результаты не смешиваются.
- **Ошибки не скрываются.** Coverage, статусы и retries публикуются рядом с accuracy. Прерванный запуск сохраняется, повторный полный запуск получает новую идентичность; нельзя выбирать лучший ответ из нескольких запусков. При инфраструктурных сбоях финальный запуск повторяется целиком, сохраняя прежние артефакты.
- **Малый размер указан явно.** В leaderboard есть `N=24`, размеры категорий и число правильных ответов. Один изменённый ответ существенно влияет на процент; MVP не требует порога качества модели, статистической значимости или вывода о языке в целом.

### pytest и GitHub Actions

Обычный CI на `push` и `pull_request` запускает валидацию датасета и `pytest` без секретов и сети. API-ответы подменяются на границе адаптера; такой подход поддерживает [pytest monkeypatch](https://docs.pytest.org/en/stable/how-to/monkeypatch.html). Проверяются положительные и отрицательные случаи scoring, сохранение казахских букв, некорректные даты/дубли ID, timeout/retry, неполные запуски, отсутствие cost при неизвестных данных и согласованность JSON/CSV/leaderboard. Проверка offline report сравнивает метрики с вручную рассчитанным небольшим fixture; тестовые ответы обозначены как синтетические и не входят в публичные результаты моделей.

Реальное сравнение выполняется локально или отдельным `workflow_dispatch` с GitHub Secrets и явным ручным запуском. Автоматические события не запускают платные API-вызовы. Workflow сохраняет все артефакты и при ошибке; завершённый опубликованный запуск хранится в репозитории без секретов, чтобы не зависеть от срока хранения Actions artifacts. Для секретов используется штатный механизм [GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets); ключи, Authorization headers и секретные URL не попадают в Git и логи. Это делает PR-проверки независимыми от наличия ключей и бюджета.

## 7. Acceptance criteria финального MVP

- [ ] В `data/benchmark.jsonl` ровно 24 вручную проверенных задания: по 8 на numbers, dates и morphology; заполнены обязательные поля, происхождение и реальная отметка проверки. Данные работодателя отсутствуют.
- [ ] Датасет и конфигурация проходят валидацию до API-вызовов. Зафиксированы версия, общий prompt, модельные параметры, зависимости и хеши.
- [ ] Один завершённый реальный запуск охватывает весь датасет минимум двумя различными моделями через официальные API. Для каждой модели coverage `24/24`; неправильные полные ответы допустимы. API-сбои и прежние неполные запуски сохранены отдельно.
- [ ] Для двух моделей имеются минимум 48 записей с исходным текстом, идентичностью модели, статусом, latency, usage либо `null`, баллами и историей попыток. Mock и синтетические ответы не выдаются за реальные.
- [ ] Accuracy, exact match, coverage и latency рассчитаны по описанным правилам, в целом и по категориям. Суммы и знаменатели сходятся с исходными записями; ошибки не исчезают из отчёта.
- [ ] Стоимость либо подтверждена и снабжена источником/расчётом, либо `null`/`N/A` с причиной. Недостоверная цена не блокирует MVP; наличие cost не является обязательным.
- [ ] Для финального запуска сохранены manifest, входные snapshot, ответы и метрики в JSON/CSV, `leaderboard.md`; корневой `LEADERBOARD.md` ссылается на этот запуск и его артефакты.
- [ ] Offline `report` без ключей и сети воспроизводит те же баллы, метрики и таблицу; ранее сохранённые ответы не изменяются. Секреты отсутствуют в файлах и логах.
- [ ] `pytest` проходит локально и в GitHub Actions на push/PR. Проверены scoring, критические ошибки runner и экспорт; обычный CI не вызывает реальные API.
- [ ] README будущей реализации описывает установку зафиксированных зависимостей, переменные окружения без значений, `validate`/`run`/`report`, запуск тестов и ограничения benchmark. Новый пользователь может повторить протокол по этим инструкциям.

MVP принимается по полноте и проверяемости pipeline. Минимальная accuracy моделей не задаётся: низкое качество является измеренным результатом, а не причиной менять датасет или правила.
